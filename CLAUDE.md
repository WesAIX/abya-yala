# abya-yala — конспект по истории коренных народов Америки

Текстово-графический конспект, начатый владельцем для самообразования и
открытый для всех. Владелец — не историк; техническая сторона репозитория
(данные, скрипты, визуализации) рассчитана на его технический бэкграунд, но
**тексты пишутся не для него**.

Язык — русский; английские термины — только устоявшиеся.

## Для кого пишем

Читатель — кто угодно: гуманитарий и инженер, школьник и пенсионер, человек,
впервые открывший тему, и тот, кто читал Хямяляйнена. Заранее о нём ничего
не известно. Поэтому:

- **Никаких аналогий из IT, техники и других узких областей** — журналы,
  подсистемы, протоколы, сети, базы данных, «баги», версии, «как в
  дистрибутивах» и тому подобное. Для человека вне этой области такое
  сравнение — странная абстракция, а не помощь. Правило касается всех
  текстов для читателя: глав, глоссария, страниц сайта и подписей
  визуализаций.
- **Пример берётся из самой темы** (наконечник из раскопа, слово, общее для
  двух языков, надпись майя) или из опыта, общего почти для всех людей
  (семья, рынок, соседи, память о дедушке).
- **Термины объясняются при первом появлении** простыми словами; без
  жаргона там, где есть обычное слово («популяция» → «группа людей,
  связанных происхождением», «модельная оценка» → «расчёт, а не прямое
  наблюдение»).
- **Термины — ссылкой на глоссарий.** Первое упоминание термина в главе —
  ссылка на его статью: `[глоттохронология](../glossary.md#глоттохронология)`.
  На GitHub это переход в глоссарий, на сайте — всплывающее краткое
  определение (`visuals/shared/article.js`). Термина нет в глоссарии —
  сначала добавить его туда: подзаголовок `### Термин`, первый абзац —
  самостоятельное короткое определение (оно и попадает в подсказку).
  Валидатор проверяет, что якорь существует.
- **Служебные слова проекта не попадают в прозу:** имена полей данных
  (`documented`, `certainty` и т. п.), названия файлов и скриптов — это для
  `data/README.md` и `CLAUDE.md`, не для глав.
- Объяснять механизмы и причины, не пересказывать учебник и не предполагать
  знания историографии — но и не упрощать до неправды.

## Главное правило: не выдумывать

- Не выдумывать даты, цифры, цитаты, атрибуции и выходные данные изданий.
  Если нет уверенности — так и писать («не удалось проверить», «по одним
  данным… по другим…») или оставлять пометку в `todo`.
- Строго разделять **факт** (со сноской), **оценку** (с именем автора) и
  **гипотезу** (с явной пометкой). Разметка — в `chapters/README.md`.
- Тезисы проекта — рабочие. Если источник их уточняет или опровергает,
  писать это прямо, а не подгонять материал под тезис.
- Источники: первичные и академические в приоритете; популярные
  (`kind: popular`) — только как дополнение и никогда как единственная опора
  для факта.
- Запись в `sources/bibliography.json` получает `"checked": true`, только
  когда выходные данные сверены с самим изданием или каталогом. Записи,
  добавленные по памяти, остаются `false`.

## Данные

- Данные отдельно от отображения: `data/*.json` или `*.csv` со ссылками на
  источники; визуализация только читает их.
- У каждой цифры — поле `sources` (`{ref, loc, note}`), `ref` — ключ из
  `sources/bibliography.json`. Не ставить ссылку, если утверждение не
  проверено по этому источнику: пустой `sources` честнее.
- У каждой даты — `dating`: `documented` / `approx` / `conventional`. До
  1500 г. — по умолчанию `approx`. Исключение (решение владельца): дата из
  датированной надписи (майя) или дендрохронологии может быть `documented`,
  но только со ссылкой на источник в `sources` — валидатор это проверяет.
- Где оценки расходятся — диапазон и автор каждой оценки, а не среднее.
- Для нового набора сначала пишется JSON Schema в `data/schema/`, затем
  запись в `DATASETS` в `tools/validate.py` (без неё валидатор считает набор
  ошибкой), затем данные.

## Визуализации

- Статический HTML + d3 с CDN (cdnjs, версия пинится), без сборки и без npm.
- Общие токены оформления — `visuals/shared/tokens.css`; цвета полос графа
  `--c-*` и цвета зон `--z-*` одинаковы во всех визуализациях. Светлая и
  тёмная темы. Новую категориальную палитру проверять валидатором навыка
  dataviz (`validate_palette.js`) для обеих тем, а не на глаз.
- Без ложной точности: этнические территории не рисуются чёткими полигонами;
  миграции — стрелками, зоны — размытыми областями; даты до 1500 г.
  показываются приблизительными.
- Подложка карт — `visuals/shared/americas-50m.geojson` (Natural Earth 1:50m,
  обрезка и упрощение — `tools/basemap.py`), никаких внешних тайлов. d3-geo
  ждёт внешние кольца полигонов по часовой стрелке — скрипт это учитывает.
- Пути к данным относительные (`../../data/…`): страница работает и локально
  (`uv run python -m http.server`), и на Pages.
- Реестр Ройса (визуализация 5): прежде чем что-то делать, найти готовые
  оцифрованные полигоны и проверить их лицензию; без этого не начинать.

## Тексты

- Связная проза о механизмах и причинах, явный вывод в конце главы; без
  воды и школьного пересказа.
- Самоназвание + устоявшееся русское название при первом упоминании в главе:
  «ленапе (делавары)».
- Сноски — `[^ключ]` с ключом из библиографии; валидатор проверяет, что ключ
  существует.
- Работа итеративная: одна глава или одна визуализация за раз. Не писать
  несколько глав заранее.

## Иллюстрации в главах — обязательны

Требование владельца: в главах **обязательно** используются графические
материалы, причём любые, которые помогают понять механизм. Это схемы,
диаграммы, графики, карты, таблицы, кадры и ссылки на интерактивные
визуализации сайта, репродукции первоисточников, фотографии. Их можно и
нужно готовить самостоятельно и вставлять в текст, не дожидаясь отдельной
просьбы. Глава без иллюстраций не считается черновиком — валидатор это
проверяет.

- **Свои рисунки** — SVG, генерируются `tools/figures.py`: функция на
  рисунок, две темы (светлая и тёмная) из `visuals/shared/tokens.css`, файлы
  `chapters/img/<NN>-<имя>-{light,dark}.svg`. В главу вставляются через
  `<picture>` с `prefers-color-scheme`, чтобы GitHub показывал версию под тему
  читателя. Числа для рисунка — из `data/` с источниками; если рисунок
  схематичен, это написано **на самом рисунке** («Схема: кривая условная»).
- **Чужие изображения** — только общественное достояние или открытые лицензии
  (CC0, CC BY, CC BY-SA). Файл кладётся в `chapters/img/`, источник
  записывается в `sources/bibliography.json` с полями `url` и `license`, а в
  подписи указываются автор, источник и лицензия. Не использовать
  изображения человеческих останков, погребений и священных предметов,
  даже если лицензия это разрешает.
- **Оформление.** У каждой иллюстрации — номер («Рис. N.M»), подпись с видом
  материала (*данные* / *схема* / *оценка*), осмысленный `alt`.
  Цветовые палитры проверяются валидатором навыка dataviz.
- **Интерактивные визуализации** сайта упоминаются в тексте ссылкой на
  `https://wesaix.github.io/abya-yala/…` рядом с тем местом, к которому они
  относятся.

## Работа над главами: агенты и команды

Писать и проверять должны разные исполнители: автор не видит своих пробелов.
Агенты лежат в `.claude/agents/`, цепочки собирают команды из
`.claude/skills/`.

- `chapter-write` — пишет главу по плану: источники до текста, разметка,
  сноски, термины, техзадание на иллюстрации.
- `chapter-figures` — рисует по техзаданию в `tools/figures.py`.
- `chapter-review` — рецензирует со свежим взглядом по двенадцати вопросам
  ниже; ничего не правит.
- `chapter-revise` — применяет готовый список замечаний минимальным дифом.
- `source-audit` — сверяет утверждения со сносками с текстами источников,
  ведёт журнал сверки; главу не правит.

```text
/new-chapter <N>      написать → нарисовать → сверить описания → рецензия ∥ сверка → правки → проверки → коммит
/review-chapter <N>   только рецензия
/audit-sources <N>    сверка описаний и утверждений, показ, правки по подтверждению
/check                все проверки
```

Разделение «найти» и «поправить» намеренное: агент, который сам ищет и сам
чинит, чинит найденное, а не важное. Рецензент и сверщик возвращают списки,
решение — за тем, кто ведёт цепочку, а спорное — за владельцем. Агенты не
коммитят: коммит делает команда, которая видит цепочку целиком. Глава после
цепочки остаётся черновиком; «принято» ставится только по слову владельца.

## Проверка содержания

Двенадцать вопросов — критерий готовности главы и чек-лист рецензента.

1. **Механизм, а не перечень.** Глава отвечает на «почему так вышло», а не
   только «что было». Перечень событий без причинной связи — недоделка.
2. **Тезис проверен, а не подогнан.** Если источники уточняют опорный тезис,
   глава говорит это прямо.
3. **Факт, оценка, гипотеза размечены.** Оценка — с автором, гипотеза — с
   пометкой. Фраза, по которой не понять, установлено это или предполагается,
   хуже честного «не проверено».
4. **У каждого факта — источник** нужного уровня: первичные и академические
   впереди, популярные — только как дополнение и не единственная опора.
5. **Без ложной точности.** Даты до 1500 г. приблизительны (кроме надписей и
   дендрохронологии со ссылкой); оценки численности — диапазоном с авторами;
   территории не очерчиваются точнее, чем известно.
6. **Имена и термины.** Самоназвание и русское название при первом
   упоминании; термины — ссылкой на глоссарий; колониальные названия
   объяснены.
7. **Понятно любому читателю.** Нет аналогий из IT и узких областей, нет
   необъяснённого жаргона и служебных слов проекта.
8. **Этика.** Нет изображений останков, погребений, священных предметов;
   нет «индейской» стилизации и стереотипов; колониальная лексика («открытие»,
   «дикари», «освоение пустых земель») — в кавычках и с разбором, а не как
   язык автора; коренные народы — действующие лица, а не фон для европейцев.
9. **Иллюстрации есть и работают.** Вид материала подписан (данные / схема /
   оценка), числа — из `data/` с источниками, схема не выдаёт себя за данные,
   точечные факты есть и в тексте; рисунок показывает то, чего не даёт текст.
10. **Связность.** Глава стыкуется с соседними, графом и глоссарием, а не
    пересказывает их.
11. **Вывод.** Явный, с честной границей: что доказано, что осталось оценкой
    или гипотезой; как это ведёт к следующей главе.
12. **Что может измениться.** Утверждения с переднего края исследований
    (генетика, новые датировки, раскопки) поданы как текущая позиция с годом
    публикации, а не как вечная истина.

## Сверка источников

Два уровня, и их нельзя смешивать.

- **Описание издания** (авторы, год, заглавие, том, страницы) —
  `checked: true` в `sources/bibliography.json` с полями `checked_via` и
  `checked_on`. Ставит `tools/bibcheck.py --apply` при полном совпадении с
  Crossref, OpenAlex или Open Library, или `source-audit` после ручной сверки
  с изданием или надёжной каталожной записью. Записи «по памяти» остаются
  `false`.
- **Утверждение по тексту источника** — журнал `sources/audits/<глава>.json`
  (схема `data/schema/audit.schema.json`). Утверждение — предложение со
  сноской, его `id` — «ключ#n» из `tools/claims.py`. Вердикты:
  подтверждено / расходится / неверная атрибуция / не подтверждено; доступ:
  полный текст / фрагмент / только описание / нет доступа. «Скорее всего
  верно» — это «не подтверждено». Аннотация подтверждает только то, что в ней
  прямо сказано; пересказ в другой работе — не подтверждение.
- Если предложение со сноской изменилось после сверки, вердикт не
  засчитывается (валидатор предупреждает) — его нужно пересверить.
- Сайт показывает на странице главы оба уровня. Статус «готово» требует,
  чтобы все описания были сверены, а все утверждения — подтверждены.
- «Не подтверждено — нет доступа» — честный и полезный результат: это список
  того, что владелец может сверить в библиотеке.
- В запросах к сторонним сервисам (каталоги, API открытого доступа) не
  передаются личные данные владельца — ни адрес почты, ни имя. Сервис,
  требующий их, не используется.

## Команды

```sh
uv sync
uv run tools/validate.py          # схемы, ссылки, сноски, покрытие источниками
uv run tools/bibliography.py      # пересобрать sources/BIBLIOGRAPHY.md (не править его руками)
uv run tools/figures.py           # перерисовать рисунки глав chapters/img/*.svg
uv run tools/claims.py chapters/<глава>.md        # утверждения со сносками и рискованное без них
uv run tools/bibcheck.py --chapter chapters/<глава>.md [--apply]   # сверка описаний с каталогами (сеть)
uv run ruff check . && uv run ruff format --check .
uv run tools/build_site.py && uv run python -m http.server -d _site   # просмотр сайта на http://localhost:8000/
uv run tools/build_site.py --drafts   # то же с черновиками — показать владельцу до принятия; не для публикации
uv run --group basemap tools/basemap.py   # пересобрать подложку карт (нужна сеть)
```

Перед коммитом все проверки (ruff, validate, `bibliography.py --check`, `figures.py --check`) должны проходить — их же запускает CI
(`.github/workflows/pages.yml`), и при ошибке сайт не публикуется.

## Публикация

GitHub Pages через Actions. Сайт собирает `tools/build_site.py` в `_site/`
(не коммитится): копирует `index.html`, `visuals/`, `data/`,
`sources/bibliography.json`, рисунки глав и превращает Markdown в страницы
сайта в его оформлении (`tools/page.html`, `visuals/shared/article.css`).
Markdown в репозитории — единственный источник текста; HTML руками не
пишется и не правится.

Жизненный цикл главы — строка `> **Статус:** …` в её начале:

| Статус | Что значит | Где видна |
|---|---|---|
| план | тезис, вопросы, источники | GitHub |
| черновик | проза и иллюстрации есть, владелец ещё не принял | GitHub |
| принято | владелец прочитал и принял; источники могут быть ещё не сверены — сайт честно пишет, сколько сверено | **сайт** |
| готово | все ссылки сверены (`checked: true`), валидатор это требует | **сайт** |

Перевод главы в «принято» делает только владелец или по его явному слову
(«принимаю главу N»). Глоссарий и библиография публикуются всегда. Ссылки
между `.md` сборщик сам превращает в ссылки на страницы сайта, а для
неопубликованных глав — на GitHub.
